# ADR-0005: 측정 근거를 바탕으로 한 AI 가설·실험 제안의 단계적 검토

## 상태

MCP 근거 분석·실험 연결 단계 마무리 (#210) / 별도 AI·RAG 제품화와 모델 비교 보류.

#202에서 계측 교차 실측, #204에서 MCP 판정 연결, #206에서 offline 제안 계약과 평가 사례를 확보했다. 실제 모델 호출·검색 평가·분석 시간 절감 검증은 아직 수행하지 않았다.

#208에서 실제 stdio MCP 조회→현재 Codex의 구조화된 제안→계약 검증→수동 SQL 진단 실측 사례를 진행했다. 단일 비맹검 세션이며 별도 LLM API/모델 평가가 아니다. 두 fresh DB 시도는 SQL 집계 횟수 불일치로 첫 warm-up에서 중단됐다. **근거 부족으로 원인 확정을 보류한 사례**로 기록하며, 다음 단계는 고정 SQL 실행 수의 직렬/병렬 대조다. 기존 read-only 권한·상위 부하 보류를 유지한다([실험 요약](../EXPERIMENTS.md#7-mcp-근거에서-선택한-sql-진단-208)).

#210의 제한된 대조에서 CLI 600 transactions의 commit 표시와 DB 누적 값은 일치했지만 병렬 digest 집계가 부족했다. 이를 업무 처리 실패나 JDBC 내부 원인 확정으로 해석하지 않는다. 기존 예매 경합으로 1회 복귀해 측정 1,804건·예상 밖 오류 0과 MCP의 자원 재검토 판정을 확인했다. 여기서 단계를 종료하며 추가 계측·AI 비교·증량을 필수 후속 작업으로 두지 않는다. 제한된 근거의 안전한 조회·분석 연결 사례이지 AI 효용이나 서버 성능 개선 성과는 아니다([실험 요약 8절](../EXPERIMENTS.md#8-제한된-sql-대조와-예매-경합-복귀-210)).

## 맥락과 재현 근거

현재 read-only MCP는 허용된 summary·manifest와 재고 불변식을 조회하고, 조건이 부족하면 비교를 거절한다. 이는 도구 인터페이스 구현이며 LLM의 분석 품질이나 사용자 효용을 입증한 결과는 아니다.

#198에서 높은 호스트 CPU peak가 관측됐지만 JVM·MariaDB 단독 병목으로 귀속하지 못했다. 정상 좌석 충돌 409, DB 잠금 대기, pool 압력, 계측 부담은 서로 다른 현상이다. 원인을 확인하지 않고 인프라나 부하를 확대할 수 없다는 판단은 ADR-0004를 따른다.

AI의 후보 역할은 측정 근거를 찾아 병목 **가설**과 이를 구분할 **다음 실험**을 제안하는 것이다. 선택 불가 좌석의 설명만 제공하는 챗봇은 현재 화면의 상태 안내와 중복되고 효용 근거가 부족해 우선하지 않는다.

## 결정

1. 우선 사람이 검토할 수 있는 실험 조건·결과를 확보한다. #200은 가상 20석, 20 iterations/s, 인기 요청 70%, Hold 500ms, seed 17을 고정하고 인기 1석/10석을 교차 반복한다. 정상 충돌과 시스템 대기를 구분하는 근거이지 서비스 처리 한계 측정은 아니다.
2. AI 도입 후보는 MCP의 검증된 구조화 지표를 조회하고, 관련 ADR·버전별 실험 조건을 근거로 가설·누락 계측·후속 실험을 제안하는 보조 흐름이다. 원인 확정은 재실험으로 수행한다.
3. 숫자·완료 여부·재고 검증은 기존 코드가 계산한다. AI 출력에는 관측 사실, 가설, 근거 ID, 반증 가능한 검증 계획을 구분한다. 조건이 다른 run을 개선 전후로 비교하지 않는다.
4. RAG는 자료 증가로 기존 고정 조회/검색에 실제 한계가 생겼을 때 검토한다. 최신·관련 버전의 ADR과 문서 근거 검색에 사용하고 현재 예약 상태·수치 계산을 vector 검색에 맡기지 않는다.
5. LLM·Spring AI·LangChain·LangGraph는 이번 Issue에서 도입하지 않는다. 실험 실행, RPS 증량, DB 변경, 결제·예약 확정은 AI에 자동 위임하지 않는다. 기존 read-only MCP의 권한도 확대하지 않는다.

## 검토한 대안

- 사람 + 기존 runner/MCP — 현재 규모에 적합한 기준 방식. 동일한 근거로 충분히 다음 실험을 선택할 수 있다면 유지한다.
- 문서 RAG와 상태 조회 챗봇 — 사용자 문제가 분명하지 않아 보류.
- AI 실험 보조 — 반복 근거 조회와 조건 비교 부담이 생길 때 후보. 정확도·비용·지연·권한 경계 검증이 추가로 필요하다.
- 자율 부하 확대/인프라 변경 — 원인 미확정과 실행 영향 때문에 채택하지 않는다.

## 결과와 trade-off

부하 실험의 가치와 AI 기술 사용을 구분한다. 현재 단계에서 AI 도입 성과나 분석 비용 절감을 주장하지 않는다. 향후 AI를 도입하면 알려진 원인 fixture와 근거 부족 fixture에서 검색 정확도, 출처 일치, 근거 없는 단정, 비교 불가 조건 거절, 실행 가능한 제안, 응답 지연·토큰 비용을 평가한다. LLM을 평가자로 쓰더라도 고정된 기대 근거·사람 검토를 함께 사용한다.

## 적용 범위와 한계

가상 좌석의 로컬 개발·실험 분석에 한정한다. 실제 운영 장애 해결, 실제 공연장 처리 용량, 실 PG 검증을 의미하지 않는다. 정상 좌석 충돌의 증가 자체를 서버 병목으로 판단하지 않는다. 인기 집합 변경은 성공/409 비율뿐 아니라 성공 시 DELETE 호출량도 바꾸므로 혼합 p95나 전체 HTTP RPS만으로 성능 개선을 주장하지 않는다.

## 재검토 조건

### Offline 제안 계약 (#206)

검증된 `assess_sampling_contrast` 보고서 → 구조화된 후보 → `evaluateExperimentProposal` 순서로 평가한다. 새 MCP 도구나 실행 권한은 추가하지 않는다. 정상 후보는 사람이 작성한 [고정 fixture](../../../tools/ticketon-evidence-mcp/test/fixtures/experiment-proposal.json)다. 실패한 실측 두 배치는 보고서에 관측값이 없어 후보 내용과 무관하게 평가를 차단한다.

| 근거 (sampling202c) | 허용하는 가설 | 다음 실험 후보 |
| --- | --- | --- |
| sequence 3/4 수집 wall-clock 6,324.735/2,915.3761ms + 자원 재검토 신호 | 호스트/수집 간섭 가능성. CPU 원인 확정 아님 | 수집 위치만 바꾸고 기존 좌석·유입량·Hold·warm-up·주기를 고정한 별도 비교 설계 |
| sequence 3/7 전역 row-lock wait 3/0 | DB 대기의 시간별 변동. 특정 SQL 병목 확정 아님 | wait 귀속 계측을 추가하는 별도 실험 설계, 추가 계측 비용도 함께 점검 |

수치·sequence·metric은 보고서와 일치해야 하며, 가설은 `HYPOTHESIS`, 결론은 `NO_CAUSAL_CONCLUSION`으로 구분한다. 제안은 가설에 대응하는 단일 변경 변수와 기존 workload 조건을 명시하고 `approvalRequired:true`, `execute:false`를 유지한다. 숫자 오인용, warm-up 인용, 미제공 CPU 지표, 확정 원인 선언, 고정 조건 누락/증량, 승인 생략, 실행 명령 삽입은 거절 사례로 정의했다.

`CONTRACT_ACCEPTED`는 구조화된 출력 계약 통과일 뿐이다. 자연어 문장의 의미, 검색 정확도, 가설의 참/거짓, 실제 실행 가능성은 사람이 별도로 검토해야 한다. 수집 위치를 옮기거나 계측을 추가하면 환경·관측 비용도 달라지므로 새 기준선이 필요하다. 이 사례의 통과율은 LLM 정확도나 작업 시간 절감으로 보고하지 않는다.

### 실제 AI/RAG 검토 전 남은 조건

- 반복 실험의 근거 조회·조건 비교·다음 실험 선택에 실제 비용이나 오류가 기록됨
- 정답/기대 근거가 정의된 평가 사례를 확보함
- 기존 조회 방식 대비 AI/RAG가 도움을 주는지를 비교할 수 있음
- 모델 호출 예산, 자료 접근 범위와 실행 승인 경계를 정의함
