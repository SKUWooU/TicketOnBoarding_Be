# ADR-0003: 서버 소유 가상 좌석 레이아웃

## 상태

승인

## 맥락과 문제

KOPIS는 이 프로젝트가 사용할 실제 좌석 배치도를 제공하지 않는다. 기존 프론트는 24석을
하드코딩하고 부하 fixture는 별도 규칙의 2,000석 번호만 생성해 두 저장소가 공유할 구조가 없었다.

## 결정

서버가 versioned 가상 레이아웃과 구역·행·순서를 소유한다. 클라이언트는 좌석 번호를 파싱하지
않고 구역 요약 및 선택 구역 상세 API를 사용한다. 메타데이터 없는 좌석은 추정하지 않고 409다.

## 검토한 대안

- 프론트 좌석 번호 파싱: 빠르지만 서버 재고와 UI 규칙이 중복된다.
- 실제 Venue/Section Entity 정규화: 현재 가상 fixture 범위에 비해 과하다.
- 2,000석 단일 응답: 호환성은 좋지만 초기 전송·렌더링 경계를 만들지 못한다.

## 결과와 trade-off

서버와 프론트가 같은 정렬·구역 계약을 공유한다. Seat row에 메타데이터가 반복되는 비용은
수용한다. 실제 좌표·등급·레이아웃 재사용이 필요해질 때 정규화 모델을 재검토한다.

## 적용 범위와 한계

가상 24석과 로컬 2,000석 fixture에만 적용한다. 실제 공연장 성능이나 운영 migration을
주장하지 않으며 WebSocket·대기열·브로커를 포함하지 않는다.

## 재검토 조건

- 실제 좌석도, 좌표·통로·등급별 가격이 필요할 때
- 공연장 레이아웃 재사용과 변경 이력이 필요할 때
- 구역당 약 200석도 브라우저 병목으로 측정될 때
